# Story 1.2: Define Hexagonal Folder Structure

Status: ready-for-dev

## Story

As a developer, I want the hexagonal architecture folder structure defined with all module directories and layer subdirectories in place, so that all team members follow consistent module boundaries (domain/application/infrastructure/interface) from the very first commit.

## Acceptance Criteria

1. The `src/modules/` directory exists with subdirectories for each bounded context: `users`, `stations`, `measurements`, `notifications`.
2. Each of the four modules contains the correct hexagonal layer subdirectories as specified in the architecture document (see detailed structure below).
3. The `src/auth/` directory exists with its flat structure and `dtos/` subdirectory (auth is NOT inside `modules/` per architecture decision).
4. The `src/shared/` directory exists with `exceptions/`, `tokens/`, and `config/` subdirectories.
5. Every leaf directory contains a `.gitkeep` file so that Git tracks the empty directories.
6. Stub NestJS module files (`*.module.ts`) are created for each module (`users.module.ts`, `stations.module.ts`, `measurements.module.ts`, `notifications.module.ts`) with minimal valid NestJS module boilerplate.
7. The `src/app.module.ts` is NOT modified in this story (wiring happens in later stories).
8. No framework imports exist in any `domain/` directory (architectural boundary respected even in stubs).
9. Running `npm run build` still succeeds after all directories and placeholder files are added.

## Dev Notes

### Project Structure Notes

The notifications module intentionally has a **different structure** than the other three modules. Per the architecture document, notifications has NO `domain/` layer and NO `interface/` layer because:
- It does not own an aggregate root (no entities, value objects, or domain ports)
- It has no REST endpoints (triggered internally via domain events)
- It only contains `application/` (ports + services) and `infrastructure/` (adapters)

The measurements module has one extra subdirectory compared to users and stations: `domain/events/` for the `MeasurementAlertDetectedEvent`.

The `auth/` module lives at `src/auth/` (NOT inside `src/modules/`) because it is a cross-cutting concern, not a bounded context with hexagonal layers.

### Stub Module File Template

Each stub module file should follow this exact pattern:

```typescript
import { Module } from '@nestjs/common';

@Module({})
export class UsersModule {}
```

Replace the class name per module: `StationsModule`, `MeasurementsModule`, `NotificationsModule`.

### Architectural Boundary Rules (for reference in later stories)

| Layer | Allowed Imports | Forbidden Imports |
|---|---|---|
| `domain/` | Pure TypeScript only | No NestJS, no Mongoose, no external deps |
| `application/` | Domain ports (interfaces), `@Injectable()` | No infrastructure, no interface layer |
| `infrastructure/` | Domain ports, Mongoose, external libs | Never imported by domain or application |
| `interface/` | Application services, DTOs, Swagger | No direct repository access |
