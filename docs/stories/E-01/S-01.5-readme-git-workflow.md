### Git Workflow Details

**Branch Naming Convention:**

| Prefix      | Purpose                        | Example                          |
|-------------|--------------------------------|----------------------------------|
| `feature/`  | New functionality              | `feature/user-authentication`    |
| `bugfix/`   | Non-urgent bug fixes           | `bugfix/fix-login-redirect`      |
| `hotfix/`   | Urgent production fixes        | `hotfix/patch-security-vuln`     |
| `docs/`     | Documentation-only changes     | `docs/update-api-readme`         |
| `chore/`    | Maintenance / tooling changes  | `chore/upgrade-nestjs`           |

**Commit Message Format (Conventional Commits):**

```
type(scope): short description

[optional body]

[optional footer]
```

Allowed types: `feat`, `fix`, `docs`, `chore`, `test`, `refactor`, `ci`, `style`, `perf`, `build`.

Examples:
- `feat(auth): add JWT token refresh endpoint`
- `fix(weather): correct temperature unit conversion`
- `docs(readme): add installation instructions`
- `test(auth): add unit tests for login service`

**PR Rules:**
- All PRs target `main` branch.
- Require at least 1 approving review.
- All CI checks (lint, tests, build) must pass before merge.
- Use squash-merge to keep `main` history clean.
- PR title should follow the same Conventional Commits format.
- PR description should include: what changed, why, and how to test.
