# Story 2.1: Restructure Repository Into Two NestJS Apps

Status: done

## Story

As a developer,
I want WeatherFlow organized as a single repository with separate API and Notification applications,
so that each component can be built, run, and deployed independently while sharing contracts safely.

## Acceptance Criteria

1. Repository uses a Nest-compatible multi-application structure with separate folders for the API and Notification service.
2. Existing Delivery I API functionality is preserved in the API application.
3. Notification-specific controllers, services, adapters, and persistence are moved under the Notification application boundary.
4. Shared code used by both applications lives in an explicit shared library or contracts folder.
5. `package.json` exposes scripts for building and starting each app independently.
6. TypeScript path aliases or imports are updated so both applications compile cleanly.
7. Existing unit tests continue to run after the restructure.
8. Architecture boundary tests are updated to understand the new app/service folders.

  - [x] 1.3 Create `libs/contracts` for DTOs/events shared across service boundaries.
  - [x] 1.4 Create `libs/shared` only for truly service-neutral utilities.

- [x] Task 2: Move the current monolith into the API app (AC: #2)

- [x] Task 3: Prepare the Notification app shell (AC: #3)
  - [x] 3.1 Create a Notification service Nest module and entrypoint.
  - [x] 3.2 Move notification-specific application, infrastructure, and interface code into the Notification app.
  - [x] 3.3 Remove direct in-process dependencies from API modules to Notification modules.

- [x] Task 4: Update build and test configuration (AC: #5, #6, #7)
  - [x] 4.1 Add `build:api` and `build:notifications` scripts.
  - [x] 4.2 Add `start:api:dev` and `start:notifications:dev` scripts.
  - [x] 4.3 Update Jest config so app and library tests are discovered.

- [x] Task 5: Update architecture validation (AC: #8)
  - [x] 5.1 Adjust architecture-boundary tests to classify `apps/api`, `apps/notifications`, and `libs/contracts`.
  - [x] 5.2 Ensure domain layers still have no NestJS, Mongoose, or transport imports.

## Dev Notes

- Prefer a clean Nest monorepo layout over a minimal second entrypoint because each service must become a distinct Docker image.
- Keep contracts stable and transport-oriented. Do not share domain entities across service boundaries.
- Do not introduce RabbitMQ behavior in this story. This story should only make the two-app structure compile and run.
