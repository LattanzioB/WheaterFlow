# Story 2.10: In-App Notification Persistence and Adapter (Extra)

Status: done

## Completion Note

Checked during S-02.10 realtime implementation: the persistence/adaptor slice was already implemented in code, including the `Notification` aggregate, Mongo repository/schema/mapper, `inApp` delivery channel, migration script, recipient resolver branch, and `InAppAlertNotifierAdapter` registration/tests. The realtime story builds on that completed slice.

> First slice of **Option E (Hybrid: Persist + Stream)** — see [S-02.9](S-02.9-build-web-ui-for-use-cases.md) for the Web UI scaffold this work builds on. This slice is **backend-only** in `apps/notifications`: it adds the storage and the new delivery adapter, so an alert reaching the service produces one persisted notification per subscribed in-app user, in parallel with the existing Telegram delivery. No browser-facing change yet — that ships in S-02.11 (REST), S-02.12 (SSE), S-02.13–14 (Web).

## Story

As the **notifications service**,
I want to **persist a `Notification` aggregate per recipient whenever a climate alert is fanned out and the recipient has the `in-app` channel enabled**,
so that **the REST history endpoint (S-02.11) and the SSE live stream (S-02.12) have a single source of truth, and re-deliveries from RabbitMQ never produce duplicates**.

## Scope

### In scope

- New `Notification` aggregate + Mongo collection in `apps/notifications`.
- New `NotificationRepository` port + Mongo adapter.
- New `inApp: boolean` field in `UserNotificationProfile.deliveryChannels`, default `true`; one-time migration backfills existing profiles.
- `UpdateDeliveryChannelsDto` and `update-delivery-channels.service` accept the new `inApp` field.
- New `InAppAlertNotifierAdapter` registered in `CompositeAlertNotifier`.
- Recipient-resolver application service emits `in-app` `NotificationDeliveryTarget`s for users whose `deliveryChannels.inApp === true`, alongside existing Telegram targets.
- Unit tests for: adapter (channel filter + persistence + repo-error isolation), repository (round-trip + pagination + duplicate-key idempotency), resolver (`inApp` enabled/disabled branches), updated update-delivery-channels service.

### Out of scope

- REST endpoints (next story, S-02.11).
- SSE endpoint (S-02.12).
- Any change in `apps/web`.
- Any change in `apps/api`.

## Acceptance Criteria

1. `Notification` aggregate with fields `{ id, userId, stationId, stationName, alertType, temperature, humidity, pressure, reportedAt, createdAt, readAt|null, messageId }` exists in `apps/notifications/src/modules/notifications/domain/entities/`.
2. Mongo collection `notifications` has indexes `{ userId: 1, createdAt: -1 }` and **unique partial** `{ userId: 1, messageId: 1 }`.
3. `NotificationRepository` port in `application/ports/` exposes `save`, `findById`, `findByUserId({ limit, cursor, unreadOnly })`, `markRead(id, userId)`, `markAllRead(userId)`; Mongo adapter implements it.
4. `save` treats `MongoServerError.code === 11000` as success (no error log), so re-delivery of the same `messageId` never duplicates rows for the same user — covered by a repository unit test.
5. `UserNotificationProfile.deliveryChannels.inApp: boolean` exists, default `true` for new profiles; an idempotent migration script `scripts/migrations/2026-05-add-in-app-channel.ts` sets `inApp = true` on every existing profile lacking the field.
6. `UpdateDeliveryChannelsDto` and `update-delivery-channels.service` (+ spec) accept and persist the new `inApp` value (unchanged if absent).
7. `InAppAlertNotifierAdapter` implements `AlertNotifier`, persists exactly one `Notification` per `in-app` target derived from the incoming `MeasurementAlertNotification`, ignores non-`in-app` targets, and a thrown repository error does not propagate beyond the adapter (composite fan-out is unaffected).
8. The adapter is registered in `CompositeAlertNotifier`'s notifier list and in `notifications.module.ts` providers.
9. The recipient-resolver application service emits an `in-app` `NotificationDeliveryTarget` (with `destination = userId`) for every subscribed user whose `deliveryChannels.inApp === true`, **in addition to** any Telegram target.
10. Unit-test coverage matches existing module standards (≥ 90% lines for the new files).
11. `docker compose up` continues to work; the `notifications` service starts and logs the new collection's index creation on first boot.

## Definition of Done

1. Publishing a synthetic `ClimateAlertDetectedMessage` to RabbitMQ (with a seeded subscribed user whose `deliveryChannels.inApp === true`) results in **exactly one** new row in the `notifications` collection for that user.
2. Re-publishing the same `messageId` does **not** create a second row.
3. All unit tests green; coverage threshold met for the new files.
4. Telegram delivery still works for the same alert (Telegram target is unaffected).
5. No change required in `apps/api` or `apps/web`.

## Dev Notes

- The `apps/api` `RecordMeasurementService` and `RabbitMqAlertPublisherAdapter` are untouched. The `RabbitMqClimateAlertConsumerAdapter` in `apps/notifications` is also untouched — it already calls the recipient resolver, which is the seam we extend.
- `CompositeAlertNotifier` already implements log-and-continue on per-adapter failure; preserve that contract for the new adapter.
- Treat `MongoServerError.code === 11000` (duplicate key) as success in `save`. This is the cheap, correct idempotency strategy and avoids an extra "processed messages" table.
- The migration script is intentionally standalone (`ts-node`); if a migrations framework gets adopted later, port it then.
