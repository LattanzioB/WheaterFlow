# Story 2.10: In-App Realtime Alert Notifications (Extra)

Status: done

## Decisions

1. Live push uses SSE, exposed as `GET /notifications/stream`.
2. Native browser `EventSource` authenticates with `?token=<JWT>`; REST endpoints use `Authorization: Bearer <token>`.
3. Idempotency uses the unique partial Mongo index on `(userId, messageId)`; duplicate key errors are treated as successful saves.
4. `deliveryChannels.inApp` defaults to `true`; the migration `scripts/migrations/2026-05-add-in-app-channel.ts` backfills existing profiles.
5. Toasts are implemented with a local React component, no extra web dependency.
6. Heartbeats are emitted every 25 seconds as SSE `ping` events.
7. Single-instance SSE fan-out is accepted for this academic deliverable; Redis pub/sub remains the future multi-instance extension point.
8. Migration remains a standalone `ts-node` script.
9. Frontend verification uses the existing TypeScript/Vite build; no Vitest setup was added to the web app.

## Implementation Notes

- The earlier backend persistence slice was already mostly present: `Notification`, Mongo repository/schema/mapper, `inApp` delivery channel, migration, resolver branch, and `InAppAlertNotifierAdapter`.
- This implementation added authenticated history/read REST endpoints, an authenticated SSE stream, EventEmitter2 live fan-out, the web `NotificationsContext`, header bell/dropdown, live toast, `/notifications` page, profile toggle, and docs updates.
- Focused unit tests were added for the new backend services, controllers, SSE controller, JWT guard, and adapter event emission.

## Story

As a **WeatherFlow subscribed user**,
I want **the Web app to receive and display the weather alerts I am subscribed to in real time**,
so that I do not depend on Telegram to find out a station I follow has crossed a threshold, and I can see a history of past alerts inside the app.

This story is a continuation of [S-02.9](S-02.9-build-web-ui-for-use-cases.md). The Web UI scaffold delivered by S-02.9 currently has no inbound channel for alerts; this story plugs the existing `notifications` service into the browser using **Option E — Hybrid (Persist + Stream)** validated 2026-05-24:

1. Persist a `Notification` document per recipient in the `notifications` service.
2. Stream live arrivals to logged-in browsers via Server-Sent Events (SSE).
3. Expose REST endpoints for history and read/unread management.
4. Add a `NotificationsContext`, header bell, toast, and `/notifications` page in `apps/web`.

No changes are required in `apps/api`. The `ClimateAlertDetectedMessage` already produced by `RecordMeasurementService` and consumed by `RabbitMqClimateAlertConsumerAdapter` is the upstream event. Telegram delivery is unaffected — `in-app` becomes a **peer** channel behind the same `AlertNotifier` port and `CompositeAlertNotifier` fan-out.

## Scope

### In scope

- New `Notification` aggregate + Mongo collection in `apps/notifications` (one document per `(userId, messageId)`, idempotent).
- New `InAppAlertNotifierAdapter` registered in `CompositeAlertNotifier`.
- New `inApp` boolean in `UserNotificationProfile.deliveryChannels`, default `true`, toggleable from the Web profile page; one-time migration backfills existing profiles.
- REST endpoints in `apps/notifications` behind `JwtAuthGuard`:
  - `GET /notifications?unreadOnly=&limit=&cursor=`
  - `PATCH /notifications/:id/read`
  - `PATCH /notifications/read-all`
- SSE endpoint `GET /notifications/stream` (JWT-authenticated, heartbeats every 25s).
- `apps/web` additions:
  - `NotificationsContext` (REST hydration on mount + SSE auto-reconnect with exponential backoff).
  - Header bell with unread badge + dropdown of latest 10 (inside existing `Layout`).
  - Toast component for live arrivals (auto-dismiss 6s, click → `/stations/:id`).
  - `/notifications` page with filters (alert type, station, unread only) and "mark read" actions.
  - `ProfilePage` toggle for the new `inApp` channel.
- Unit tests for: in-app adapter, Mongo notification repository (with duplicate-key idempotency), recipient resolver `inApp` branch, REST controllers, SSE controller.
- One integration test: publish a `ClimateAlertDetectedMessage` to RabbitMQ → assert a notification row exists for the seeded subscribed user → assert an SSE subscriber receives the event.
- Docs updates: C4 Component delta, sequence diagram "Climate alert → in-app delivery", ER diagram extension for `Notification`, SSE contract section in `docs/api-reference.md`.

### Out of scope (unless explicitly approved)

- **Web Push (VAPID)** — browser background/offline delivery. Deferred to a future story; this story only delivers to a foreground tab.
- **Email** delivery channel.
- **WebSocket gateway** — SSE chosen for one-way push simplicity.
- **Horizontal scaling of the SSE endpoint** — single `notifications` instance is acceptable for the academic deliverable. If multi-instance becomes a requirement, fan-out via Redis pub/sub is the agreed extension point (out of scope here).
- Changes to `apps/api` or the existing `ClimateAlertDetectedMessage` contract.
- Reimplementing alert threshold logic in the frontend.
- Production-grade design system or accessibility certification.
- E2E browser tests (covered by manual demo script; can be a follow-up).

## Proposed Approach (validate before implementation)

| Concern           | Proposal                                                                       | Alternatives                           |
| ----------------- | ------------------------------------------------------------------------------ | -------------------------------------- |
| Live push         | Server-Sent Events (`text/event-stream`)                                       | WebSocket gateway (Socket.IO), polling |
| SSE auth          | JWT via `Authorization` header on `EventSource` polyfill OR signed query token | Short-lived cookie                     |
| In-process bridge | Existing `EventEmitter2` (already in `NotificationsAppModule`)                 | RxJS subject, Redis pub/sub            |
| Idempotency       | Unique partial index on `(userId, messageId)`                                  | App-level dedupe table                 |
| Pagination        | Cursor on `createdAt + _id`                                                    | Offset pagination                      |
| Web state         | New `NotificationsContext` (parallel to `AuthContext`)                         | Zustand, redux-toolkit                 |
| Toast             | Local component (no library)                                                   | `react-hot-toast`, `sonner`            |

Heartbeat interval: **25s** (under typical idle proxy timeouts). Reconnect backoff: 1s → 2s → 5s → 15s capped.

## Acceptance Criteria

1. A `Notification` aggregate with fields `{ id, userId, stationId, stationName, alertType, temperature, humidity, pressure, reportedAt, createdAt, readAt|null, messageId }` is persisted in a `notifications` collection with indexes `{ userId: 1, createdAt: -1 }` and unique partial `{ userId: 1, messageId: 1 }`.
2. `UserNotificationProfile.deliveryChannels` includes an `inApp: boolean` flag, default `true` for new profiles; a migration script sets `inApp = true` on every existing profile lacking the field; the value is editable through the existing `UpdateDeliveryChannelsDto`.
3. The recipient resolver returns an `in-app` `NotificationDeliveryTarget` (with `destination = userId`) for every subscribed user whose `deliveryChannels.inApp === true`, **alongside** any Telegram target already produced.
4. `InAppAlertNotifierAdapter` implements `AlertNotifier`, persists exactly one notification per `in-app` target, is registered inside `CompositeAlertNotifier`, and a failure in this adapter does not prevent other adapters (e.g., Telegram) from delivering.
5. Re-delivery of the same `ClimateAlertDetectedMessage` (same `messageId`) does **not** create duplicate notification rows for the same user — verified by an integration test.
6. `GET /notifications?unreadOnly=&limit=&cursor=` returns the authenticated user's notifications paginated, newest first; `PATCH /notifications/:id/read` marks one as read (404 if not owned); `PATCH /notifications/read-all` marks every unread for the caller. All endpoints are behind `JwtAuthGuard` and documented with `@ApiProperty` / `@ApiResponse`.
7. `GET /notifications/stream` returns `Content-Type: text/event-stream`, authenticates via JWT (header or query param), emits an `event: notification` payload to the connected user within **2 seconds** of the upstream RabbitMQ publication, and sends a `: ping\n\n` heartbeat every 25s. The connection is closed cleanly on logout/unsubscribe.
8. The Web app opens the SSE stream after login, hydrates with the latest 20 unread via REST, survives a transient disconnect (auto-reconnect with backoff), and tears the stream down on logout.
9. The header (in `Layout`) shows a bell icon with the unread count; clicking it opens a dropdown of the latest 10 notifications; each row links to `/stations/:stationId`; a "View all" link navigates to `/notifications`.
10. Every live arrival shows a non-blocking toast for 6 seconds with the alert type, station name, and a click target opening the station detail page.
11. A `/notifications` page lists the full history with filters (alert type, station, unread only), shows an empty state, and exposes per-row "mark read" plus a bulk "mark all read" action.
12. `ProfilePage` exposes an "In-app notifications" toggle bound to the new `inApp` flag.
13. The integration test (Jest + dockerized RabbitMQ + Mongo) covers: publish `ClimateAlertDetectedMessage` → notification row persisted for the seeded subscribed user → SSE subscriber receives the matching event.
14. Architecture artifacts updated: C4 Component delta, sequence diagram "Climate alert → in-app delivery", ER diagram extended with the `Notification` collection, and an SSE section in `docs/api-reference.md`.
15. `docker compose up` continues to work — no new infra services required; the Web image keeps building.

## Dev Notes

- The `apps/api` side stays untouched. The contract `ClimateAlertDetectedMessage` and the topic exchange settings are reused as-is.
- `CompositeAlertNotifier` is the **only** infrastructure seam — adding the in-app adapter to its constructor list is the wiring change.
- SSE under NestJS: use `@Sse('stream')` (`@nestjs/common`) returning `Observable<MessageEvent>`; combine the per-user filter with `takeUntil(close$)` to ensure cleanup.
- Native browser `EventSource` cannot send custom headers — that is why JWT in query string is acceptable here. Use a short-lived dedicated SSE token if you do not want to expose the access token (out of scope, but flag it in the Decisions section if the team chooses to add it).
- Idempotency: when `MongoServerError.code === 11000` is thrown by the unique partial index, treat it as success (no error log) — it means the same alert was re-delivered.
- For backpressure, if a subscriber buffers more than N events without reading, drop the connection — frontend will reconnect and re-hydrate from REST. Keep this simple; do not invent a queue per user.
- Frontend reconnect: rely on the browser's built-in `EventSource` reconnect for transient drops; add a manual exponential backoff layer only after the browser has given up (i.e., the `error` event is emitted twice consecutively).
