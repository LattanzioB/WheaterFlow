# Story 2.11: In-App Notifications — REST History Endpoints (Extra)

Status: draft

> Slice 2 of **Option E (Hybrid: Persist + Stream)**. Depends on [S-02.10](S-02.10-in-app-notification-persistence-and-adapter.md) (persistence + `NotificationRepository`). This slice adds the read-side REST surface so the Web app (S-02.13/S-02.14) can hydrate history and manage read/unread state.

## Story

As an **authenticated WeatherFlow user**,
I want **REST endpoints to list, paginate, and mark my notifications as read**,
so that **the Web app can show a history view and an unread-count badge that survives reloads and reconnections**.

## Scope

### In scope

- Three endpoints in `apps/notifications`, all behind `JwtAuthGuard`:
  - `GET /notifications?unreadOnly=&limit=&cursor=`
  - `PATCH /notifications/:id/read`
  - `PATCH /notifications/read-all`
- DTOs (`list-notifications.query.dto.ts`, response DTO, route param DTO) with `class-validator` and `@ApiProperty` decorators.
- Application services: `ListUserNotificationsService`, `MarkNotificationReadService`, `MarkAllNotificationsReadService` (+ specs).
- Controller + spec.
- Ownership enforcement: `PATCH /notifications/:id/read` returns 404 if the notification is not owned by the caller; `mark-all` is scoped to the caller's `userId`.
- Swagger documentation visible at the existing notifications service `/api/docs`.

### Out of scope

- SSE endpoint (next story, S-02.12).
- Any change in `apps/web` (consumed in S-02.13).
- Soft-delete or archive (history is append-only here).

## Acceptance Criteria

1. `GET /notifications` returns the caller's notifications sorted by `createdAt DESC`, paginated by opaque cursor. Default `limit = 20`, max `100`.
2. `GET /notifications?unreadOnly=true` returns only notifications with `readAt === null`.
3. Response shape includes: `items: NotificationResponseDto[]`, `nextCursor: string|null`, `unreadCount: number` (total unread for the caller across all pages).
4. `PATCH /notifications/:id/read` returns `204` and sets `readAt` to `now()` if the notification belongs to the caller; returns `404` otherwise (no information leak about other users' notifications).
5. `PATCH /notifications/read-all` returns `204` and marks every currently-unread notification owned by the caller as read (atomic enough — single Mongo `updateMany`).
6. All three endpoints require `JwtAuthGuard`; unauthenticated requests return `401`.
7. DTOs are decorated with `@ApiProperty` (descriptions + examples), `class-validator` (`IsBoolean`, `IsInt`, `Min`, `Max`, `IsOptional`, `IsString`), and `class-transformer` (`Type`).
8. Endpoints appear in Swagger at the notifications service `/api/docs` under a `Notifications` tag, with `@ApiBearerAuth()` and `@ApiResponse` for `200`/`204`/`401`/`404`.
9. Unit tests cover: cursor pagination correctness, `unreadOnly` filter, ownership-404 path, mark-all updates only the caller's rows.
10. No change to `apps/api`, `apps/web`, or the existing notification-preferences endpoints.

## Definition of Done

1. A user with persisted notifications (seeded via S-02.10) can `GET /notifications`, mark one read, and mark all read using Swagger UI with a JWT bearer.
2. Trying to `PATCH /notifications/:id/read` on another user's id returns `404`.
3. All unit tests green.
4. Swagger reflects all three endpoints under `Notifications` with auth and response codes.

## Dev Notes

- Cursor implementation: `(createdAt|_id)` packed and base64-encoded; if the repository already exposes a paginate helper, reuse it; otherwise add a thin `paginate` helper in the repository spec'd here so the cursor encoding stays in one place.
- `unreadCount` in the response is the **total** unread for the caller, not just unread-in-this-page; compute it with a separate `countDocuments({ userId, readAt: null })` in `list-user-notifications.service`.
- Authorization model is the same as existing user-notification-preferences endpoints — copy that controller's JWT setup verbatim to avoid drift.
