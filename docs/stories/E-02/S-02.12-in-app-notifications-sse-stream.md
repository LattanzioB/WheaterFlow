# Story 2.12: In-App Notifications — SSE Live Stream (Extra)

Status: draft

> Slice 3 of **Option E (Hybrid: Persist + Stream)**. Depends on [S-02.10](S-02.10-in-app-notification-persistence-and-adapter.md) (the new adapter produces the in-process event we relay). REST history (S-02.11) is independent and can be developed in parallel. The Web consumer ships in S-02.13.

## Story

As the **notifications service**,
I want to **expose a JWT-authenticated SSE endpoint that pushes each newly persisted in-app notification to its owning user's open browser tabs in under 2 seconds**,
so that **subscribed users see weather alerts in real time inside the Web app without polling**.

## Scope

### In scope

- `GET /notifications/stream` returning `Content-Type: text/event-stream`.
- JWT auth on the SSE endpoint:
  - Prefer `Authorization: Bearer <token>` header when present (for non-native clients).
  - Accept `?token=...` query parameter as a fallback (native `EventSource` cannot set headers).
- In-process bridge: `InAppAlertNotifierAdapter` (from S-02.10) emits an `EventEmitter2` event `notification.delivered` carrying `{ userId, notification }`; the SSE controller filters by authenticated `userId` and pushes a `notification` SSE event.
- Heartbeat: send `: ping\n\n` every 25 seconds to keep idle proxies from closing the connection.
- Clean teardown on client disconnect (subject unsubscribe).
- Unit tests for: per-user filtering, heartbeat firing, teardown on disconnect, auth (401 when missing/invalid token).

### Out of scope

- Persistence (done in S-02.10).
- REST history (S-02.11).
- Multi-instance fan-out (single notifications instance is sufficient for the academic deliverable; documented as a future extension via Redis pub/sub).
- Replaying events the client missed while disconnected — the Web consumer (S-02.13) catches up via `GET /notifications` (S-02.11).
- Per-user buffer/backpressure beyond "drop oldest" inside `EventEmitter2` defaults.

## Acceptance Criteria

1. `InAppAlertNotifierAdapter` (S-02.10) is extended (or a small wrapper service is added) to emit an in-process `notification.delivered` event after a successful `save`, carrying `{ userId: string, notification: NotificationResponseDto }`.
2. A new `NotificationStreamController` exposes `@Sse('notifications/stream')` returning an `Observable<MessageEvent>`.
3. The endpoint is authenticated:
   - Reuses `JwtAuthGuard` when the `Authorization` header is present.
   - Accepts a `?token=...` query parameter; the resolved `userId` matches the JWT subject and equals the SSE filter key. Invalid/expired token → `401`.
4. The controller subscribes to `EventEmitter2.on('notification.delivered', ...)`, filters by `userId === authUser.id`, and emits a `MessageEvent` with `type: 'notification'` and `data: notification` JSON.
5. A heartbeat `MessageEvent` is sent every 25 seconds (`{ type: 'ping' }` or a comment line `: ping`); confirm by a fake-timer unit test.
6. When the client disconnects (request `close` event), the `EventEmitter2` listener is removed and any per-connection timers are cleared — no listener leak across reconnects (verified by a unit test that opens and closes N connections and asserts the listener count returns to baseline).
7. End-to-end timing target: from `RabbitMqAlertPublisher.publishClimateAlert(...)` to SSE delivery in the subscribing user's connection is **under 2 seconds** in the local docker environment (measured in the integration test in S-02.15, but the unit-test path here must keep the synchronous portion under 50ms to make 2s achievable).
8. The endpoint appears in Swagger at `/api/docs` under the `Notifications` tag with `@ApiBearerAuth()` and an `@ApiQuery({ name: 'token', required: false })`; payload shape documented in the description.
9. No change to `apps/api`, `apps/web`, or persistence behavior.

## Definition of Done

1. Curl against `http://localhost:3001/notifications/stream?token=<jwt>` keeps an open connection, prints a `ping` comment every 25s, and prints a `notification` event within 2 seconds of publishing a `ClimateAlertDetectedMessage` to the local RabbitMQ exchange.
2. All unit tests green.
3. Swagger UI shows the new endpoint and its payload shape.
4. No listener leaks after repeated connect/disconnect cycles.

## Dev Notes

- NestJS's `@Sse()` decorator returns whatever `Observable<MessageEvent>` you produce — keep the controller method body small; compose the observable in a private helper or in the application service.
- `EventEmitter2` is already imported in `NotificationsAppModule` via `EventEmitterModule.forRoot()` — no new dependency.
- `EventSource` (native browser) cannot send headers, hence the query-token fallback. To avoid leaking the access token in URLs and logs, the Web consumer (S-02.13) should request a **short-lived SSE-only token** from a future endpoint; that endpoint is out of scope here — for now, the access token is acceptable for the academic deliverable. Flag this in the **Decisions** section of S-02.13 when the team picks the final approach.
- Heartbeat: a comment line (`: ping\n\n`) is invisible to `EventSource.onmessage`, which is what we want.
