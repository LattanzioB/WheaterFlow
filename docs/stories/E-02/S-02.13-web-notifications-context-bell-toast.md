# Story 2.13: Web — NotificationsContext, Header Bell, and Toast (Extra)

Status: draft

> Slice 4 of **Option E (Hybrid: Persist + Stream)**. Depends on [S-02.11](S-02.11-in-app-notifications-rest-history.md) (REST history) and [S-02.12](S-02.12-in-app-notifications-sse-stream.md) (SSE stream). Brings the alerts into the user's browser as a header bell + dropdown + live toast. The full-page history view and the profile toggle ship next in S-02.14.

## Story

As a **logged-in WeatherFlow user using the Web app**,
I want **a bell in the header that shows an unread count and a toast for incoming alerts**,
so that **I notice alerts on stations I am subscribed to without leaving the page I am on**.

## Scope

### In scope

- New `NotificationsContext` (parallel to the existing `AuthContext`) in `apps/web/src/notifications/`.
  - Exposes `notifications`, `unreadCount`, `markRead(id)`, `markAllRead()`, `refresh()`.
  - Hydrates with `GET /notifications?limit=20` on login mount.
  - Opens an `EventSource` to `/notifications/stream?token=<jwt>` on login; reconnects with exponential backoff after the browser's own retries fail; closes on logout.
- Typed API client methods added to `apps/web/src/api/weatherflow.ts`:
  - `fetchNotifications({ unreadOnly?, limit?, cursor? })`
  - `markNotificationRead(id)`
  - `markAllNotificationsRead()`
- Type additions to `apps/web/src/api/types.ts`: `Notification`, `NotificationsPage`.
- New `NotificationsBell` component in `apps/web/src/components/` mounted inside the existing `Layout` header.
  - Bell icon (inline SVG, no new dependency).
  - Badge with unread count (hidden when zero).
  - Click opens a dropdown with the latest 10 notifications (one row per item, click → `/stations/:stationId`).
  - "Marcar todas como leídas" action at the bottom of the dropdown.
  - "Ver todas" link → `/notifications` (route is added by S-02.14, but rendering "View all" here is fine — it will 404 until S-02.14 ships; document this in the Decisions section of S-02.14).
- New `Toast` component in `apps/web/src/components/` and a thin host (`ToastHost`) mounted at the root of `Layout`.
  - Fires on each new live notification (i.e., `notifications[0]` changes after the initial hydration).
  - Auto-dismiss in 6s; click navigates to `/stations/:stationId`.
  - Manual dismiss via close button.
- `App.tsx` provider stack: `<AuthProvider> > <NotificationsProvider> > <BrowserRouter>`.

### Out of scope

- `/notifications` history page (next story, S-02.14).
- Profile toggle for the `inApp` channel (S-02.14).
- Frontend unit tests beyond a smoke render — S-02.9 set the no-frontend-tests precedent; revisit only if requested.
- Accessibility audit beyond keyboard-focus on the bell and dropdown.
- Theme / styling rework.

## Acceptance Criteria

1. After login, the header (in `Layout`) shows a bell icon. When `unreadCount > 0`, a badge displays the count (capped visually at `99+`).
2. Hydration on mount calls `GET /notifications?limit=20` and stores the result. `unreadCount` comes from the response's `unreadCount` field, not from counting `items`.
3. `EventSource` connects to `${VITE_API_NOTIFICATIONS_BASE_URL}/notifications/stream?token=<jwt>` (env var defaults to `http://localhost:3001`); on receiving an event `notification`, the payload is prepended to `notifications` and `unreadCount` is incremented.
4. On every new live arrival, a toast appears in the bottom-right for 6 seconds with the alert type, station name, and a click that calls `navigate('/stations/' + stationId)` then dismisses.
5. The bell dropdown opens on click, lists up to 10 latest notifications newest-first, distinguishes unread (subtle dot/background) from read, and closes on outside-click or `Esc`.
6. The "Marcar todas como leídas" action calls `PATCH /notifications/read-all`, then `refresh()`.
7. Clicking a notification row calls `markRead(id)` and navigates to `/stations/:stationId` (then dismisses the dropdown).
8. On `AuthContext` logout, the `EventSource` is closed, the context is reset to its initial state, and the bell hides.
9. After `EventSource` `error` events that lead the browser to give up reconnecting, the context attempts a manual reconnect with delays of `1s → 2s → 5s → 15s` (capped). Each manual reconnect also re-issues the hydration `GET /notifications?limit=20`.
10. No new runtime npm dependencies beyond what `apps/web/package.json` already includes.
11. `docker compose up` still builds the Web image.

## Dev Notes

- `EventSource` reconnects on its own for transient drops. The manual exponential backoff only kicks in after the browser's `error` event indicates the connection cannot be re-established (typically after the second error in a row).
- Keep `NotificationsContext` provider-only logic (no JSX outputs) so storybook/devtools renders cleanly.
- Bell + dropdown must NOT introduce a portal library — use a simple absolute-positioned panel; existing `apps/web` styles are minimal CSS, match them.
- A typical pitfall: the toast fires once per state change. Use a monotonically increasing `lastLiveArrivalId` and dedupe inside `ToastHost` to avoid duplicate toasts on a re-render.
