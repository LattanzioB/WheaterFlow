# Story 2.14: Web — Notifications Page and Profile Toggle (Extra)

Status: draft

> Slice 5 of **Option E (Hybrid: Persist + Stream)**. Depends on [S-02.13](S-02.13-web-notifications-context-bell-toast.md) (`NotificationsContext` + bell + toast). Adds the full-history page and lets the user opt out of in-app delivery from `ProfilePage`.

## Story

As a **logged-in WeatherFlow user**,
I want **a `/notifications` page with full history and filters, and a profile toggle to disable in-app notifications**,
so that **I can review past alerts in depth and stop receiving in-app delivery if I only want Telegram**.

## Scope

### In scope

- New `/notifications` route + `NotificationsPage.tsx` in `apps/web/src/pages/`.
  - Paginated list (cursor-based, consuming `nextCursor` from the REST DTO).
  - Filters: alert type (multi-select), station (single-select among the user's subscribed stations), `unreadOnly` toggle.
  - Per-row "Marcar como leída" action; bulk "Marcar todas como leídas" button.
  - Empty state ("Sin notificaciones todavía") and loading state.
- Side-nav entry "Notificaciones" added to `Layout`.
- `App.tsx` route `/notifications`.
- `ProfilePage` extended with an "Notificaciones en la app" toggle bound to the `inApp` channel in `deliveryChannels`.
- API client extension for the in-app channel toggle:
  - `updateDeliveryChannels({ telegram?, inApp? })` mapped to the existing `PATCH /users/:id/notification-preferences/delivery-channels` (S-02.10 added the `inApp` field on the backend).

### Out of scope

- Re-implementing notification persistence or SSE (done in earlier slices).
- Notification grouping/sorting beyond newest-first.
- Frontend tests (S-02.9 precedent).
- Soft-delete or archive UI.

## Acceptance Criteria

1. `/notifications` is a protected route accessible only to authenticated users (uses existing `ProtectedRoute`).
2. The page hydrates via `fetchNotifications({ limit: 20 })`, sorted newest-first; a "Cargar más" button appends the next page using `nextCursor`.
3. Filters:
   - Alert type multi-select using `ALERT_TYPE_LABELS` from `apps/web/src/api/types.ts`.
   - Station single-select populated from the user's subscribed stations.
   - `Solo no leídas` toggle.
   - Changing any filter resets pagination.
4. Each row shows: alert type, station name, timestamp (`reportedAt`), key readings, an "unread" marker if `readAt === null`.
5. Per-row "Marcar como leída" calls `markRead(id)`; the row's read state updates without a full reload.
6. Bulk "Marcar todas como leídas" calls `markAllRead()` and updates the page state.
7. Empty state renders when the filtered list is empty after a successful fetch.
8. Side-nav (in `Layout`) shows a "Notificaciones" entry with the bell icon and the unread count badge from `NotificationsContext`.
9. `ProfilePage` shows an "Notificaciones en la app" toggle reflecting the user's `deliveryChannels.inApp`; toggling it calls the existing delivery-channels PATCH endpoint and updates the displayed value optimistically.
10. After disabling `inApp`, a new triggered alert no longer produces a new in-app notification (verified manually by re-running the "Demo alerta" preset from S-02.9 and seeing the bell badge NOT increment, while Telegram still delivers when configured).
11. No new runtime npm dependencies.

## Dev Notes

- "Live update from SSE while user is on `/notifications`": when `NotificationsContext` prepends a new notification, `NotificationsPage` should reflect it at the top of the current view (because the list is a derived view of the context's `notifications`). Avoid maintaining a separate page-local list — read from the context.
- Optimistic toggle: keep the previous value in local state, call `setUser`-equivalent (or `refreshUser()`) on success; on error, revert local state and `setError(message)`.
- Subscribed-station selector reuses `fetchSubscriptions(user.id)` already used by `SubscriptionsPage`.
