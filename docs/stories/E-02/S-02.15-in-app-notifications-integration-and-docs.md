# Story 2.15: In-App Notifications — Integration Test and Architecture Docs (Extra)

Status: done

> Final slice of **Option E (Hybrid: Persist + Stream)**. Depends on [S-02.10](S-02.10-in-app-notification-persistence-and-adapter.md) through [S-02.14](S-02.14-web-notifications-page-and-profile-toggle.md). Closes the feature with one cross-boundary integration test and refreshes the architecture artifacts so the C4, sequence, and ER diagrams reflect the new collection, channel, and SSE endpoint.

## Story

As a **Delivery III reviewer of WeatherFlow**,
I want **an integration test that exercises the api → RabbitMQ → notifications → SSE → persistence loop, plus updated architecture artifacts**,
so that **I can verify the in-app notification feature works end-to-end without manual Postman steps and understand the new shape of the system from the diagrams**.

## Scope

### In scope

- Integration test `apps/notifications/test/in-app-fanout.int-spec.ts`:
  - Boots the `notifications` service against the dockerized RabbitMQ + Mongo from `docker-compose.yml`.
  - Seeds a `UserNotificationProfile` with one subscribed station and `deliveryChannels.inApp = true`.
  - Opens an SSE client to `/notifications/stream?token=<jwt>`.
  - Publishes a `ClimateAlertDetectedMessage` to the configured exchange/routing key.
  - Asserts: notification row persisted, SSE client receives the matching `notification` event within 2 seconds, second publish with the same `messageId` does NOT duplicate the row.
- Architecture documentation refresh:
  - C4 Component diagram updated to show the new `Notification` collection, the `InAppAlertNotifierAdapter`, the SSE endpoint, and the Web consumer.
  - New sequence diagram `Climate alert → in-app delivery` showing api → RabbitMQ → consumer → resolver → composite notifier → in-app adapter → SSE → browser.
  - ER diagram extended with the `notifications` collection (fields + indexes) and the `deliveryChannels.inApp` field on the profile.
  - SSE + REST endpoints documented in `docs/api-reference.md` under a new "In-app notifications" section.
- E-02 README index marks S-02.10 through S-02.15 as `done` when this story closes.

### Out of scope

- E2E browser tests (S-02.9 precedent: manual demo).
- New features.
- Load tests for the SSE endpoint.

## Acceptance Criteria

1. `npm run test:int -w apps/notifications` (or the existing equivalent script) runs the new test against a live RabbitMQ + Mongo (via `docker compose up rabbitmq mongo`) and passes locally.
2. The test fails fast (within 5s) when RabbitMQ or Mongo are not reachable, with a clear error message naming the missing service.
3. The test asserts:
   - A `notifications` row exists for the seeded user with `messageId === <published messageId>`.
   - The SSE client receives a `notification` event whose `messageId` matches.
   - A second publish with the same `messageId` does NOT create a second row (idempotency).
4. `docs/architecture/` contains updated C4 Component source files (`.drawio` or `.puml` or `.mmd`) plus exported images, showing the new components.
5. `docs/architecture/sequence-climate-alert-in-app-delivery.*` (source + image) exists and illustrates the full path described above.
6. The ER diagram source + image in `docs/architecture/` includes the `notifications` collection (with its two indexes) and the new `inApp` field in delivery channels.
7. `docs/api-reference.md` has an "In-app notifications" section listing:
   - `GET /notifications` (query params, response DTO, examples).
   - `PATCH /notifications/:id/read`.
   - `PATCH /notifications/read-all`.
   - `GET /notifications/stream` (SSE contract: event names, payload shape, heartbeat interval, auth surface).
8. `docs/stories/E-02/README.md` table is updated so S-02.10–S-02.15 are listed with status `done` upon merge of this story.

## Dev Notes

- Prefer the existing dev `docker-compose.yml` services over spinning new containers per test; the test should assume they are up and skip with a helpful message otherwise (no `testcontainers` if avoidable).
- Use the project's diagramming tool of choice — match what `docs/architecture/` already uses (look at the existing C4 source extension to decide).
- The SSE contract documentation should be the authoritative source for the Web team. Spell out:
  - `event: notification` payload shape (JSON of `NotificationResponseDto`).
  - Heartbeat: `: ping` comment line every 25s.
  - Reconnect expectations: browsers auto-reconnect; clients should re-hydrate via `GET /notifications` on each successful (re)connect.
  - Auth surface decided in S-02.12 / S-02.13 (header preferred, `?token=` accepted for native `EventSource`).
