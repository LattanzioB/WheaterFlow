# Story 2.3: Define Shared Contracts And Alert Publisher

Status: draft

## Story

As the API service,
I want to publish a complete climate-alert message to RabbitMQ when a measurement triggers an alert,
so that the Notification service can process notifications without internal module calls or cross-service database joins.

## Acceptance Criteria

1. A shared `ClimateAlertDetectedMessage` contract exists in `libs/contracts`.
2. The contract contains all data required by the Notification service to notify recipients.
3. API service defines an alert publisher port used by `RecordMeasurementService`.
4. RabbitMQ publisher adapter implements the alert publisher port.
5. The existing in-process `EventEmitter2` notification flow is removed from the alert delivery path.
6. Measurement saving remains successful even if notification dispatch is asynchronous.
7. Unit tests verify publishing happens only when a measurement has an alert.
8. Publisher failures are handled according to an explicit policy and documented.

## Tasks / Subtasks

- [ ] Task 1: Define the integration contract (AC: #1, #2)
  - [ ] 1.1 Create `ClimateAlertDetectedMessage` in `libs/contracts`.
  - [ ] 1.2 Include `messageId`, `occurredAt`, `measurementId`, `stationId`, `stationName`, `alertType`, `reportedAt`, `temperature`, `humidity`, and `pressure`.
  - [ ] 1.3 Avoid exporting domain entities or value objects in the contract.

- [ ] Task 2: Add an alert publisher port in the API service (AC: #3)
  - [ ] 2.1 Define `AlertPublisher` as a port interface.
  - [ ] 2.2 Add an injection token for the publisher.
  - [ ] 2.3 Inject the publisher into `RecordMeasurementService`.

- [ ] Task 3: Publish from measurement recording (AC: #5, #6)
  - [ ] 3.1 Build the message after the measurement is saved.
  - [ ] 3.2 Publish only when `measurement.hasAlert()` is true.
  - [ ] 3.3 Remove direct dependency on the Notification module and EventEmitter notification handler.

- [ ] Task 4: Implement RabbitMQ adapter (AC: #4, #8)
  - [ ] 4.1 Add RabbitMQ client dependency and connection configuration.
  - [ ] 4.2 Publish to a configured exchange/routing key.
  - [ ] 4.3 Document whether publisher errors fail the request or are logged after persistence.

- [ ] Task 5: Add tests (AC: #7)
  - [ ] 5.1 Update `RecordMeasurementService` tests to assert alert messages are published.
  - [ ] 5.2 Add a no-alert test that asserts no message is published.
  - [ ] 5.3 Add publisher adapter unit tests with a mocked RabbitMQ channel/client.

## Dev Notes

- Recommended failure policy: measurement persistence succeeds first; publishing errors should be surfaced or logged explicitly. If no outbox is implemented, document the residual risk.
- A future outbox pattern would be more robust, but it may be too much for this academic delivery unless time allows.
- The message should be rich enough that the Notification service does not need to read the API service database for measurement/station details.
