# Story 2.4: Extract Notification Service APIs And Persistence

Status: draft

## Story

As a user,
I want to manage notification subscriptions and delivery channels through the distributed system,
so that notification preferences are owned by the Notification service while existing user workflows remain mostly compatible.

## Acceptance Criteria

1. Notification service owns subscription, alert preference, delivery-channel, and Telegram/linking data.
2. Notification service exposes REST endpoints for managing notification preferences.
3. API service no longer persists notification preferences or delivery channels as part of the user aggregate.
4. Existing routes can remain as API proxy routes where useful, but the actual notification state is managed remotely.
5. Notification service persistence uses its own Mongo collection(s).
6. Notification service validates that preferences contain user and station identifiers without importing API domain internals.
7. Unit tests cover preference creation, updates, deletion, and delivery-channel configuration.
8. API docs clearly show any route changes or proxy behavior.

## Tasks / Subtasks

- [ ] Task 1: Define notification-owned data model (AC: #1, #5)
  - [ ] 1.1 Create a notification preference aggregate/model in the Notification service.
  - [ ] 1.2 Store `userId`, `stationId`, selected `alertTypes`, and delivery targets.
  - [ ] 1.3 Add Mongo schema, mapper, and repository adapter.

- [ ] Task 2: Move notification use cases (AC: #1, #7)
  - [ ] 2.1 Move subscribe, unsubscribe, update alert preferences, and update delivery channels into the Notification service.
  - [ ] 2.2 Keep use cases independent from API domain entities.
  - [ ] 2.3 Add unit tests for each use case.

- [ ] Task 3: Expose Notification service REST API (AC: #2)
  - [ ] 3.1 Add endpoints for listing subscriptions by user.
  - [ ] 3.2 Add endpoints for subscribe/unsubscribe/update alert types.
  - [ ] 3.3 Add endpoint for delivery-channel configuration.
  - [ ] 3.4 Keep Telegram endpoints optional or hidden if real Telegram is not needed.

- [ ] Task 4: Integrate with API routes where compatibility matters (AC: #4)
  - [ ] 4.1 Decide which existing `/users/:id/...` routes should proxy to Notification service.
  - [ ] 4.2 Add an API-side HTTP client adapter for Notification service calls.
  - [ ] 4.3 Preserve authentication/ownership checks at the API boundary.

- [ ] Task 5: Remove notification state from API user ownership (AC: #3, #6)
  - [ ] 5.1 Stop new API writes to user notification preference fields.
  - [ ] 5.2 Keep backward-compatible migration handling if existing mock data contains old fields.
  - [ ] 5.3 Ensure API domain does not import Notification service code.

- [ ] Task 6: Update API docs (AC: #8)
  - [ ] 6.1 Document final route map.
  - [ ] 6.2 Document whether routes are direct Notification service routes or API proxy routes.

## Dev Notes

- Minor route changes are allowed, but existing workflows should remain easy to demo.
- Preferred public shape:
  - API keeps `/users/me` for identity/profile.
  - Notification service exposes `/notification-preferences/users/:userId/subscriptions`.
  - API may proxy old `/users/:id/subscriptions` routes to reduce client disruption.
- Since Telegram is not mandatory, delivery can support a `log` or `mock` target for local verification.
