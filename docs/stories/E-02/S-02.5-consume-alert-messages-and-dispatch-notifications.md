# Story 2.5: Consume Alert Messages And Dispatch Notifications

Status: ready for review

## Story

As the Notification service,
I want to consume climate-alert messages from RabbitMQ and notify matching subscribers,
so that climate alerts are handled asynchronously through a real service boundary.

## Acceptance Criteria

1. Notification service connects to RabbitMQ and consumes `ClimateAlertDetectedMessage` messages.
2. Consumer validates incoming message shape before processing.
3. Notification service resolves subscribers by `stationId` and `alertType`.
4. Users without configured delivery targets are skipped.
5. A fake/log notifier is implemented for local demos and tests.
6. Telegram adapter remains optional and is not required for Delivery II success.
7. Unit tests cover consumer behavior, preference filtering, missing targets, malformed messages, and notifier calls.
8. Failed message handling is explicit: ack, nack, retry, or dead-letter behavior is documented.

## Dev Notes

- This story is where the project satisfies the mandatory queue publication/consumption requirement.
- Keep the consumed message as an integration DTO, then map it into Notification service application models.
- Avoid importing API application services, API repositories, or API domain entities.

## Implementation Notes

- `RabbitMqClimateAlertConsumerAdapter` connects to the configured RabbitMQ URL, asserts the durable climate-alert exchange and notification queue, binds the queue to the routing key, and consumes with `noAck: false`.
- Runtime validation is provided by `validateClimateAlertDetectedMessage` in `libs/contracts`, keeping the shared DTO primitive and checking required strings, ISO date strings, finite numeric readings, and supported alert types.
- Failure policy: valid messages are acked only after notification processing succeeds. Malformed messages and processing failures are nacked with `requeue=false`; RabbitMQ will dead-letter them when the queue is configured with a dead-letter exchange, otherwise the broker drops them.
- `NotificationService` now handles the rich `ClimateAlertDetectedMessage` directly and no longer reads API measurement or station repositories.
- Local demos use `LogAlertNotifierAdapter` by default through `NOTIFICATION_DELIVERY_MODE=log`; Telegram remains optional and skips external calls when `TELEGRAM_BOT_TOKEN` is not configured.
