# Story 2.9: Build Web UI For Use Cases (Extra)

Status: done

## Story

As a **WeatherFlow end user** (operator or demo reviewer),
I want a **web interface** that executes the system's main use cases against the existing REST API,
so that I can demonstrate Delivery II functionality without relying only on Swagger, Postman, or curl.

This story implements the **optional assignment requirement** (“interfaz de usuario que permita ejecutar los casos de uso”). It does **not** change domain rules or service boundaries; the UI is a thin client over `apps/api`.

## Scope

### In scope

- New frontend app under `apps/web/` (monorepo sibling to `api` and `notifications`).
- Authentication flows: register, login, logout, session persistence (JWT in browser storage).
- Use-case screens mapped to documented API routes in `docs/api-reference.md`:
  - Profile (`GET /users/me`).
  - Weather stations: list (owned + available), create, view, update, delete, name filter.
  - Measurements: create, list with filters, delete; surface `alertStatus` / `alertType` after create.
  - Subscriptions: list, subscribe, update alert types, unsubscribe.
  - Delivery channels: **deferred** — Telegram/link-code UI omitted in this delivery (validated 2026-05-22).
- Guided **“Demo alerta”** section with preset measurement values for each alert type (Calor Extremo, Helada, Tormenta, Humedad Critica).
- API CORS enabled for local dev origins.
- README / setup instructions for running API + web together.
- Optional: Vite dev-server proxy to API to avoid CORS during development.

### Out of scope (unless explicitly approved)

- Calling the Notification service directly from the browser (preferences go through API proxy routes only).
- Reimplementing alert threshold logic in the frontend.
- Telegram webhook configuration UI or RabbitMQ management embedded in the app.
- Production-grade design system, i18n, or accessibility certification.
- E2E browser tests (can be a follow-up story).
- Docker image for the web app in `docker-compose.yml` (proposed as optional Task 8).

## Proposed Stack (validate before implementation)

| Build | Vite | — |

Default API base URL: `http://localhost:3000` (env `VITE_API_BASE_URL`).

## Acceptance Criteria

1. Unauthenticated users can **register** and **login**; JWT is stored and sent on protected requests.
2. Authenticated users see a **dashboard / navigation** with sections: Perfil, Mis estaciones, Estaciones disponibles, Mediciones, Suscripciones, Notificaciones.
3. **Stations — owned**: list with optional name filter; create station; edit status/name/location/sensor; delete station.
4. **Stations — available**: list stations discoverable for subscription (`GET /weather-stations/available`) with name filter.
5. **Measurements**: create measurement for a selected owned station; response shows computed alert fields; list measurements with filters (station name, temp/humidity/pressure min/max, date range, alert-only); delete measurement.
6. **Subscriptions**: subscribe to a station with selected `alertTypes`; list current subscriptions; patch alert types; unsubscribe.
7. **Subscriptions** (profile section): view `notificationPreferences` from `GET /users/me` alongside subscription management. Telegram / delivery-channel forms are **out of scope** for this story.
8. **Demo alerta**: one screen or panel with buttons that pre-fill measurement form values for each alert rule (and one “sin alerta” baseline).
9. API errors (`400`, `401`, `404`, `409`) are shown with the server `message` in the UI.
10. `docs/api-reference.md` or README links to how to run the web app locally.
11. API enables CORS for `http://localhost:5173` (Vite default) and documents `CORS_ORIGINS` in `.env.example` if configurable.

## Dev Notes

- Swagger remains the technical API explorer; this UI is the **business-facing** executor of use cases.
- `ownerId` on station create should default to the authenticated user id from `GET /users/me` (do not expose arbitrary owner selection unless API requires it).
- Alert types in subscription UI must match API enum: `Ninguna`, `Calor Extremo`, `Helada`, `Tormenta`, `Humedad Critica`.
- After Delivery II split, subscription routes on port 3000 are **proxied** to the Notification service; the web app only talks to port 3000.
- Seed data (`npm run seed:swagger-mock-data`) can accelerate demos once login credentials are documented.
