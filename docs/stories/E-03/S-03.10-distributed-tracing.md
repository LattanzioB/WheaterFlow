# Story 3.10: Distributed Tracing — OpenTelemetry Across Ingestion→API→Queue

Status: draft

## Story

As an operator,
I want a single distributed trace that spans from an ingestion poll to the published alert and notification,
so that I can follow one request across services and pinpoint where latency or failures occur.

## Acceptance Criteria

1. `api`, `notifications`, and `ingestion` are instrumented with the OpenTelemetry Node SDK and auto-instrumentation (HTTP, Nest/Express, `amqplib`, Mongoose).
2. Trace context propagates over **HTTP** (ingestion→API intake) and **AMQP** (API→RabbitMQ→notifications) so the requirement "follow a request from ingestion to the alert published on the queue" is met as one connected trace.
3. A Jaeger service is added to `docker-compose.yml`; all services export spans to it via OTLP (directly or through an OTel Collector).
4. Spans are named meaningfully and carry attributes (station id, alert type, cycle id, OWM result) without leaking secrets.
5. Resilience events are visible in traces: timeouts, breaker-open short-circuits, retries, and fallback/cache hits appear as span events/attributes.
6. `traceId`/`spanId` are available to the logger (S-03.8) so logs and traces correlate.
7. A documented end-to-end example trace (poll → record → publish → dispatch) is captured for the architecture docs (S-03.14).
8. Instrumentation is togglable via env and adds no functional change when disabled.

## Tasks / Subtasks

- [ ] Task 1: OTel bootstrap (AC: #1, #3, #8)
  - [ ] 1.1 Add an OTel SDK bootstrap loaded before Nest in each service.
  - [ ] 1.2 Configure the OTLP exporter and a service-name resource attribute.
  - [ ] 1.3 Add `jaeger` (and optionally `otel-collector`) to `docker-compose.yml`.

- [ ] Task 2: Context propagation (AC: #2)
  - [ ] 2.1 Ensure HTTP client/server propagation on the ingestion→API hop.
  - [ ] 2.2 Inject/extract trace context into RabbitMQ message headers across publish/consume.

- [ ] Task 3: Span enrichment + resilience visibility (AC: #4, #5)
  - [ ] 3.1 Add attributes (station id, alert type, cycle id, OWM result).
  - [ ] 3.2 Emit span events for timeout/breaker/retry/fallback from S-03.6.

- [ ] Task 4: Correlation + docs (AC: #6, #7)
  - [ ] 4.1 Expose `traceId`/`spanId` to the logger.
  - [ ] 4.2 Capture an end-to-end trace screenshot/description for the docs.

## Dev Notes

- The AMQP propagation is the crux of the end-to-end requirement: inject the trace context as message headers in the API publisher and extract it in the notifications consumer.
- A direct OTLP→Jaeger export is enough for an academic delivery; an OTel Collector is optional but keeps exporters uniform.
- Load the SDK via a `--require`/preload entry so auto-instrumentation patches libraries before they are imported.
