# Historia 3.15: Documentación de arquitectura de la Entrega III

Estado: en progreso (solo falta AC #7: evidencia de una semana de datos)

## Historia

Como revisor, quiero documentación sincronizada con la solución final, para
comprender la evolución arquitectónica y reproducir la demostración.

## Criterios de aceptación

1. C4 muestra API, notificaciones, ingesta, OWM y observabilidad.
2. Se justifican los desintegradores que motivan el componente independiente.
3. Hay secuencias para:
   - ingesta periódica (cron → OWM → API → persistencia),
   - alerta por medición OWM (API → RabbitMQ → notificaciones),
   - **temperatura actual** (cliente → API → ingesta → OWM → respuesta),
   - **promedios diario/semanal** (cliente → API → MongoDB → respuesta).
4. Swagger documenta proveedor, origen, endpoint interno y reportes.
5. Se documentan las estrategias de resiliencia y sus fronteras (OWM, API ↔
   ingesta).
6. Se documentan logs, métricas, tracing, reglas de alertas y dashboard.
7. Se adjuntan resultados de carga y evidencia de al menos una semana de datos.
8. README explica arranque, configuración, URLs y recorrido de demo.
9. Diagramas, enlaces y referencias pasan las validaciones del repositorio.

## Implementación

- **C4 (AC #1, #9):** `docs/architecture/c4/c4_level_2_container.plantuml`
  agrega un `System_Boundary` de observabilidad (Prometheus, Grafana, Loki,
  Jaeger, Alertmanager) con sus relaciones hacia API/Notifications/Ingestion;
  se regeneró el PNG. `docs/architecture-overview.md#diagrams` corrige el link
  roto a `docs/architecture/c4/architecture.md` (antes apuntaba a
  `arquitectura.md`, inexistente). Se agregó además
  `c4_level_3_ingestion.plantuml` (con su PNG), el nivel 3 que faltaba para
  Ingestion: desglosa scheduler, controllers internos, `RunIngestionCycleService`
  y los tres adaptadores resilientes (catálogo de estaciones, proveedor OWM,
  submitter de mediciones), documentado en `architecture.md`.
- **Desintegradores (AC #2):** nueva sección "Why Ingestion Is a Third
  Independent Service" en `architecture-overview.md`, con una cuarta fila de
  granularity breaker (failure domain isolation, change cadence, operational
  scaling) que completa la tabla ya usada para justificar API/Notifications en
  la Entrega II.
- **Secuencias (AC #3):** se crearon
  `docs/architecture/sequences/current-temperature-report-sequence.mmd` y
  `temperature-average-report-sequence.mmd` (+ SVG), y se corrigió un error de
  sintaxis Mermaid en `scheduled-ingestion-sequence.mmd` que impedía
  renderizarlo. La alerta disparada por una medición OWM reutiliza el mismo
  pipeline documentado en `record-measurement-alert-sequence.mmd`; se agregó
  una nota explícita en "Key Flows" en vez de duplicar el diagrama, ya que no
  existe un camino de alerta distinto para datos externos.
- **Swagger (AC #4):** se agregó `@ApiTags`/`@ApiOperation` a los controllers
  de Reports (`station-temperature-reports`, `temperature-average-reports`),
  Internal Ingestion (`internal-ingestion-stations`,
  `internal-ingestion-measurements`), `measurements` y `weather-stations`, para
  que el Swagger UI agrupe estas secciones en vez de quedar sin tag. Los DTOs
  de estación/medición ya documentaban `provider`/`source` como enum vía
  `@ApiProperty` desde S-03.1/S-03.9.
- **Resiliencia (AC #5):** nueva sección "Resilience Strategies" en
  `architecture-overview.md` con una tabla que cruza las 5 estrategias
  (timeout, breaker, bulkhead, fallback/cache, retry) contra las 3 fronteras
  (OWM, ingestion→API, API→ingestion), enlazando a S-03.7/S-03.8 para el
  detalle y la cobertura de tests.
- **Observabilidad y alerting (AC #6):** se expandió "Observability Stack" con
  una tabla de los 4 pilares (logs, métricas, tracing, alerting), la tabla de
  reglas Prometheus y la política de Alertmanager (agrupación, ventanas,
  inhibición), enlazando a `observability/README.md` como runbook operativo.
- **Carga (AC #7, parcial):** nueva sección "Load Test Evidence" con la tabla
  de los 3 escenarios k6 y enlace al baseline versionado. La evidencia de una
  semana de datos OWM reales **queda pendiente**: depende del despliegue de
  ingesta continua sobre el cluster Atlas compartido por el equipo, que aún no
  lleva una semana corriendo al momento de escribir esta historia. Se dejó un
  callout explícito en `architecture-overview.md` señalando el pendiente en
  vez de simular datos.
- **Demo y README (AC #8):** `docs/setup.md` agrega una sección
  "Observability Profile" dedicada y una sección "Demo Walkthrough" con 8
  pasos reproducibles (levantar stack, ingesta manual, reportes en Swagger,
  disparar alerta, ver traza en Jaeger, ver dashboard, forzar una alerta
  operativa deteniendo un servicio, correr carga).
- **Validaciones del repositorio (AC #9):** se encontraron y corrigieron 4
  suites de test de documentación ya rotas en `main`, sin relación con esta
  historia (drift de la migración Mermaid → PlantUML del C4 y SVGs de UML
  nunca generados): `c4-architecture-docs.spec.ts` se reescribió para validar
  los `.plantuml` actuales en vez de archivos Mermaid eliminados;
  `c4-component-docs.spec.ts` se corrigió restaurando el nombre del adaptador
  `HttpNotificationServiceClient` en el diagrama y ajustando una aserción que
  esperaba controllers (`AuthController`, etc.) fuera del alcance real de ese
  diagrama; se generaron los SVG faltantes de `weatherflow-domain-model.mmd` y
  `weatherflow-ports-adapters.mmd`. `sequence-diagrams-docs.spec.ts` gana un
  nuevo `describe` que valida los 3 diagramas de Entrega III.
