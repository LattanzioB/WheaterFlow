# Historia 3.16: Vinculación Telegram en la web y prueba E2E del conector de alertas

Estado: en progreso (UI y runbook listos; falta ejecutar la prueba E2E con bot real y adjuntar evidencia)

## Historia

Como usuario suscripto a alertas, quiero vincular mi cuenta de Telegram desde
la web y recibir las alertas en mi chat, para validar de punta a punta el
conector de alertas por Telegram que hasta ahora solo está cubierto por tests
unitarios.

## Contexto

El backend del conector ya existe desde la Entrega II y no requiere cambios de
dominio:

- `TelegramAlertNotifierAdapter` envía `sendMessage` a los targets con canal
  `telegram` (`apps/notifications/.../telegram-alert-notifier.adapter.ts`).
- `POST /notifications/telegram/webhook` procesa updates con secret token y
  resuelve el comando `/link CODE`
  (`telegram-webhook.controller.ts`, `process-telegram-webhook.service.ts`).
- `POST /users/:id/delivery-channels/telegram/link-code` genera el código de
  vinculación y `PATCH /users/:id/delivery-channels` gestiona los canales
  (proxied vía API).
- `GET /users/me` expone `deliveryChannels.telegram.chatId` (`null` si no está
  vinculado).
- Las variables `TELEGRAM_BOT_TOKEN`, `TELEGRAM_BOT_USERNAME` y
  `TELEGRAM_WEBHOOK_SECRET` ya están en `.env.example` y `docker-compose.yml`.

Lo que falta: la UI de vinculación quedó explícitamente fuera de alcance en
S-02.9 ("Telegram UI omitido", validado 2026-05-22) y el flujo completo nunca
se probó contra un bot real de Telegram.

## Criterios de aceptación

1. La página de perfil en `apps/web` muestra el estado del canal Telegram
   (vinculado / no vinculado) a partir de `deliveryChannels.telegram.chatId`
   de `GET /users/me`.
2. Un botón "Generar código de vinculación" invoca
   `POST /users/:id/delivery-channels/telegram/link-code` y muestra el código,
   su expiración y las instrucciones: enviar `/link CODE` al bot
   `@TELEGRAM_BOT_USERNAME`.
3. Tras completar la vinculación por Telegram, la UI refleja el estado
   vinculado al recargar el perfil (no se requiere tiempo real).
4. El usuario puede desvincular / desactivar el canal Telegram desde la UI
   usando el contrato existente de `PATCH /users/:id/delivery-channels`.
5. Los errores de la API (`400`, `401`, `404`, `409`) se muestran con el
   `message` del servidor, siguiendo el patrón de las páginas existentes.
6. Existe un runbook que documenta cómo exponer el webhook en entorno
   local/demo con un túnel (ngrok o cloudflared) hacia el servicio de
   notificaciones: `setWebhook` con `secret_token`, verificación con
   `getWebhookInfo` y limpieza posterior (`deleteWebhook`).
7. Se ejecuta y documenta con evidencia (capturas) la prueba E2E real:
   generar código en la web → `/link CODE` al bot → disparar una medición que
   produce alerta (presets de `/demo`) → el mensaje llega al chat de Telegram
   vinculado.
8. El webhook sigue rechazando requests sin el secret token correcto
   (comportamiento ya implementado; cubierto por los tests existentes que
   deben permanecer en verde).

## Implementación

- `apps/web/src/pages/ProfilePage.tsx`: sección Telegram en "Canales de
  entrega" — estado vinculado/no vinculado desde
  `deliveryChannels.telegram.chatId`, generación del código con expiración e
  instrucciones (`/link CODE` + link al bot), verificación por recarga del
  perfil (`GET /users/me`) y desvinculación con
  `PATCH /users/:id/delivery-channels` (`telegram.chatId: null`). Errores con
  `message` del servidor vía `ErrorBanner`, botones deshabilitados durante las
  llamadas.
- `apps/web/src/pages/profile-page-state.ts` (+ spec): helpers puros de estado
  de página — `getTelegramChannelStatus`, `isLinkCodeExpired`,
  `buildLinkCommand`, `describeBotDestination` — siguiendo el patrón de
  `notifications-page-state`.
- `apps/web/src/api/weatherflow.ts` / `types.ts`: `createTelegramLinkCode` y
  el tipo `TelegramLinkCode` (contrato de
  `POST /users/:id/delivery-channels/telegram/link-code`).
- `docs/notifications/telegram-webhook-runbook.md`: túnel (ngrok/cloudflared),
  `setWebhook` con `secret_token`, `getWebhookInfo`, prueba E2E, chequeo
  negativo del secret y `deleteWebhook`.
- Sin cambios de backend: el webhook y su validación de secret quedan como
  estaban (tests existentes en verde).
