# Historia 3.19: Separación experimental de la BD de Notificaciones y comparación de carga

Estado: desarrollado

## Historia

Como desarrollador, quiero comparar el rendimiento del servicio de
Notificaciones cuando comparte la base Atlas con el resto del sistema contra
cuando tiene su propia base MongoDB local, para decidir con datos si aislar su
persistencia mejora la latencia y el throughput bajo carga.

## Contexto

Hoy `api`, `notifications` (e `ingestion` solo vía HTTP) comparten una única
conexión Mongo a través de la misma variable `MONGODB_URI` (config key
`database.uri`), tanto en `.env` (Atlas) como en `docker-compose.yml` (default
local `mongodb://mongo:27017/weatherflow`). El servicio de Notificaciones ya es
dueño exclusivo de dos colecciones lógicamente aisladas — `notifications` y
`user_notification_profiles`
(`apps/notifications/src/modules/.../persistence/*.schema.ts`) — sin joins ni
lecturas cruzadas desde `api` (confirmado en `docs/architecture-overview.md`).
Esto hace que separar físicamente su base sea solo un cambio de configuración
(otra URI de conexión), no de código: no hace falta tocar
`notifications-app.module.ts`, `env-validation.ts` ni `configuration.ts`.

Es un experimento de performance, no un cambio de arquitectura permanente:
`docker-compose.yml` y `.env.example` quedan sin tocar. El contenedor Mongo
adicional y la variable de entorno distinta para `notifications` se documentan
como procedimiento local ad-hoc.

Los datos de notificaciones se generan disparando el pipeline real de alertas
(no existe un endpoint público para crear notificaciones directamente):
`AlertEvaluator.evaluate()`
(`apps/api/src/modules/measurements/domain/services/alert-evaluator.service.ts`)
dispara `AlertType.EXTREME_HEAT` cuando `Temperature.isExtremeHeat()` es
verdadero, es decir `temperature > 40`
(`temperature.value-object.ts:17`). `DEFAULT_ALERT_SETTINGS`
(`libs/shared/src/domain/alert-settings.ts`) trae `extremeHeat: true` por
defecto, así que una estación recién creada ya acepta esa alerta sin
configuración extra. El flujo completo: `POST /measurements` con
`temperature > 40` en una estación suscripta → API publica en RabbitMQ →
`RabbitMqAlertPublisherAdapter` → consumer de Notificaciones → se persiste un
`Notification` y se hace fan-out.

## Criterios de aceptación

1. Existe un script k6 nuevo y dedicado,
   `scripts/load-tests/notifications-load.js`, separado de
   `scripts/load-tests/weatherflow-load.js`, con `npm run test:load:notifications`.
2. El `setup()` registra un usuario, crea una estación y lo suscribe a
   `EXTREME_HEAT` vía
   `POST /notification-preferences/users/:userId/subscriptions/:stationId`.
3. Cada iteración combina una operación de escritura real (measurement con
   `temperature > 40` que dispara alerta vía RabbitMQ) con operaciones de
   lectura/escritura sobre el servicio de Notificaciones:
   `GET /notifications`, `PATCH /notifications/:id/read`,
   `PATCH /notifications/read-all`,
   `GET /notification-preferences/users/:userId`.
4. Hay umbrales versionados de p95, tasa de error y throughput, y los
   resultados se escriben en `docs/load-tests/notifications-latest-summary.json`
   y `docs/load-tests/notifications-latest-report.html` (nombres separados de
   los del script de mediciones).
5. Existe documentación (`docs/load-tests/notifications-README.md`) que explica
   cómo levantar un contenedor Mongo local adicional
   (`weatherflow-mongo-notifications`, puerto `27018`) y repuntar solo la
   `MONGODB_URI` del proceso/contenedor `notifications` hacia él, dejando `api`
   sin cambios.
6. Se ejecutan y documentan dos corridas comparables:
   - **Escenario A**: `api` y `notifications` sobre la misma base Atlas
     compartida (estado actual).
   - **Escenario B**: `notifications` sobre el contenedor Mongo local propio;
     `api` sin cambios respecto de A.
   Ambas corridas parten de bases de notificaciones vacías y usan el mismo
   dataset/VUs/duración.
7. El README nuevo incluye una tabla comparativa final (p95 por endpoint, tasa
   de error, throughput) entre Escenario A y Escenario B.
8. No hay cambios en `apps/notifications/src/**`, `docker-compose.yml` ni
   `.env.example`: el split queda fuera de la configuración commiteada.
