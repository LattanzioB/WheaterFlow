# Story 3.2: Internal Ingestion Intake Endpoint Reusing The Domain Pipeline

Status: draft

## Story

As the ingestion service,
I want a system-authenticated API endpoint that records externally sourced readings through the existing domain pipeline,
so that OpenWeatherMap data is validated, alert-evaluated, persisted, and published exactly like manual measurements without duplicating domain logic.

## Acceptance Criteria

1. The API exposes an internal intake endpoint (e.g. `POST /internal/ingestion/measurements`) that accepts a reading for a station id (temperature, humidity, pressure, observedAt).
2. The endpoint runs the existing `RecordMeasurementService` so threshold validation, alert detection, persistence, and `ClimateAlertDetectedMessage` publication happen unchanged.
3. Recorded readings are tagged `source=openweather`.
4. The endpoint is authenticated with a system credential (e.g. `INGESTION_API_KEY` via a guard), **not** the public JWT flow, and does **not** enforce station ownership (the public `POST /measurements` ownership check does not apply to system ingestion).
5. The endpoint validates the station exists and is `provider=openweather`; unknown or non-OWM stations are rejected with a clear error.
6. Invalid payloads are rejected with 400 and a descriptive message.
7. The endpoint is documented in Swagger (or explicitly marked internal) and covered by controller + service unit tests.
8. The change keeps the public measurement endpoint and its ownership rule intact.

## Dev Notes

- `RecordMeasurementService` already persists first and publishes the alert after; reuse it verbatim. Only the `source` argument is new (added in S-03.1).
- Keep the intake DTO primitive and separate from the public `CreateMeasurementDto` to avoid coupling internal and public contracts.
- The endpoint is the API-side half of the own-component remote boundary; fault tolerance for the caller side is added in S-03.6.
