# Historia 3.3: Estructura base del servicio de ingesta y Docker

Estado: completada

## Historia

Como desarrollador, quiero una aplicación NestJS independiente para la ingesta,
para aislar el scheduling y las fallas de OWM de la API de usuarios.

## Criterios de aceptación

1. Existe `apps/ingestion` con capas de aplicación, dominio e infraestructura.
2. Hay scripts de build, desarrollo y pruebas.
3. La configuración valida `OWM_API_KEY`, `OWM_BASE_URL`, `API_BASE_URL`,
   `INGESTION_CRON` y límites de concurrencia.
4. Docker Compose levanta el worker junto con API y notificaciones.
5. La aplicación expone health check y respeta las fronteras arquitectónicas.
6. No importa entidades de dominio desde otras aplicaciones.

## Implementación

- `apps/ingestion` es una aplicación NestJS independiente, con módulo raíz,
  módulo de ingesta y carpetas `application`, `domain` e `infrastructure`.
- El proceso expone `GET /health` en `INGESTION_PORT` (por defecto `3002`).
- La configuración falla rápido si faltan `OWM_API_KEY`, `OWM_BASE_URL` o
  `API_BASE_URL`, y valida el cron y ambos límites de concurrencia.
- Docker Compose construye `apps/ingestion/Dockerfile`, espera que la API esté
  saludable y no conecta el worker directamente con MongoDB ni RabbitMQ.
- Las pruebas verifican configuración, health, wiring del módulo, Compose y la
  prohibición de importar código de dominio o implementación desde las otras
  aplicaciones.

La consulta real a OpenWeather, el scheduler y el envío de mediciones a la API
quedan reservados para S-03.4, S-03.5 y S-03.6.
