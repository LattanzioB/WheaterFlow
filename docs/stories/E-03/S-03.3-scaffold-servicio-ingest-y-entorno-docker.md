# Historia 3.3: Scaffold del servicio ingest y entorno Docker

Estado: borrador

## Historia

Como desarrollador,
quiero una tercera aplicación NestJS para ingesta climática externa con su propia imagen Docker,
para que el polling de OWM corra como componente independiente con comunicación remota hacia la API, consistente con las fronteras de la Entrega II.

## Criterios de aceptación

1. `apps/ingest` existe con entrypoint NestJS, estructura de módulos y carpetas hexagonales alineadas con las convenciones de la API.
2. `package.json` expone `build:ingest`, `start:ingest:dev` y test scripts para la nueva app.
3. La configuración del servicio ingest usa `@nestjs/config` con validación Joi para env vars requeridas (`OWM_API_KEY`, `API_BASE_URL`, `INGEST_CRON`, etc.).
4. `docker-compose.yml` construye y levanta el servicio ingest junto a API, notifications, RabbitMQ y conectividad MongoDB.
5. El contenedor ingest depende de la disponibilidad de la API (health check u orden de arranque documentado).
6. Los contratos compartidos en `libs/contracts` siguen siendo el único mecanismo de tipos entre servicios; sin imports de entidades de dominio entre apps.
7. Los tests de fronteras arquitectónicas clasifican `apps/ingest` correctamente.
8. La app ingest vacía arranca exitosamente en Docker Compose sin errores de runtime.
