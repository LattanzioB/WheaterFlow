# Historia 3.4: Adaptador HTTP de OpenWeatherMap

Estado: completada

## Historia

Como servicio de ingesta, quiero consultar OWM mediante un puerto propio, para
desacoplar el caso de uso del contrato y transporte del proveedor y reutilizarlo
tanto en la ingesta programada (S-03.5) como en consultas síncronas de
temperatura actual (S-03.9).

## Criterios de aceptación

1. Existe el puerto `WeatherDataProvider`.
2. El adaptador consulta Current Weather API por latitud y longitud.
3. La respuesta se normaliza a una lectura con temperatura, humedad, presión,
   timestamp e identificador externo.
4. Las unidades se tratan explícitamente.
5. Errores HTTP y payloads inválidos producen errores tipados.
6. Hay fixtures y pruebas para éxito, 4xx, 5xx, timeout y respuesta inválida.
7. El puerto es invocable desde el job programado y desde el endpoint interno
   de S-03.9 sin duplicar lógica HTTP.

## Implementación

- `WeatherDataProvider` define `getCurrentWeather()` por latitud y longitud y
  devuelve una lectura independiente del contrato de OpenWeather.
- `OpenWeatherMapAdapter` consulta `/data/2.5/weather` con `units=metric`; la
  instancia HTTP agrega `appid` y aplica `OWM_TIMEOUT_MS`.
- `OpenWeatherMapResponseMapper` normaliza `id`, `dt`, `main.temp`,
  `main.humidity` y `main.pressure` con unidades explícitas: `celsius`,
  `percent` y `hPa`.
- Los errores se clasifican como `client_error`, `server_error`, `timeout`,
  `unavailable` o `invalid_payload`, sin filtrar Axios ni el payload específico
  del proveedor hacia los consumidores del puerto.
- `IngestionModule` exporta `WEATHER_DATA_PROVIDER_TOKEN`, listo para ser
  inyectado por el proceso programado de S-03.5 y el endpoint interno de S-03.9.
- Los fixtures y tests cubren respuesta exitosa, 4xx, 5xx, timeout y payload
  inválido.
