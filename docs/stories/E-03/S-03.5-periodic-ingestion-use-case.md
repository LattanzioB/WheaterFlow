# Story 3.5: Periodic Ingestion Use Case (Poll → Record → Alert, End To End)

Status: draft

## Story

As the ingestion service,
I want each scheduled cycle to poll OpenWeatherMap for every provider-backed station and push readings to the API,
so that external measurements flow through the domain pipeline and can trigger alerts and notifications automatically.

## Acceptance Criteria

1. An `IngestStationReadings` cycle use case lists provider-backed stations (via the API or a shared read path) and, for each, fetches OWM and sends the reading to the API intake endpoint from S-03.2.
2. Stations are resolved by their OWM association and polled using their stored coordinates.
3. Each successful reading results in one measurement recorded by the API with `source=openweather`; an OWM reading that breaches a threshold produces a `ClimateAlertDetectedMessage` and a delivered notification, with no changes to that pipeline.
4. A failure for one station does not abort the cycle for the others (per-station isolation).
5. The cycle is idempotent enough for repeated runs (no crash on duplicate/again-polled data) and logs a per-cycle summary (polled, recorded, skipped, failed).
6. The configurable schedule from S-03.3 drives the cadence; a manual trigger exists for demos/tests.
7. An integration-style test demonstrates the full path with OWM and the API stubbed: poll → intake → recorded measurement (and alert when the reading breaches a threshold).
8. Unit tests cover station iteration, per-station failure isolation, and the cycle summary.

## Tasks / Subtasks

- [ ] Task 1: Resolve the polling set (AC: #1, #2)
  - [ ] 1.1 Add an `IngestionApiClient` method (or read path) to list `provider=openweather` stations.
  - [ ] 1.2 Extract coordinates for each station.

- [ ] Task 2: Cycle use case (AC: #1, #3, #4, #5)
  - [ ] 2.1 For each station: fetch via `WeatherProviderClient`, then post to the intake endpoint.
  - [ ] 2.2 Isolate per-station errors; continue the loop on failure.
  - [ ] 2.3 Accumulate and log a structured per-cycle summary.

- [ ] Task 3: Triggers (AC: #6)
  - [ ] 3.1 Wire the scheduler tick to the cycle use case.
  - [ ] 3.2 Add a manual trigger (internal endpoint or CLI) for demos.

- [ ] Task 4: Tests (AC: #7, #8)
  - [ ] 4.1 End-to-end test with stubbed OWM + stubbed API intake: a normal reading is recorded.
  - [ ] 4.2 End-to-end test: a threshold-breaching reading drives an alert through the pipeline.
  - [ ] 4.3 Unit test: one station failing does not stop the others; summary counts are correct.

## Dev Notes

- The cycle must call the API intake endpoint (S-03.2) rather than touching Mongo directly, so the domain pipeline stays authoritative and the boundary stays remote.
- Keep resilience policy (timeouts, breaker, bulkhead, fallback, cache) out of this story; it is layered in S-03.6 around the same clients.
- Trace context propagation for the end-to-end trace is added in S-03.10; design the clients so headers can be injected later.
