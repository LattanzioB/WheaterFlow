# Story 3.7: Temperature Report Endpoints (Current, Last-Day Avg, Last-Week Avg)

Status: draft

## Story

As an API consumer,
I want three temperature report endpoints for a station/location,
so that I can read the current temperature and the average temperature over the last day and the last week.

## Acceptance Criteria

1. Three endpoints exist on the API: current temperature, average temperature of the last day, and average temperature of the last week, for a given station (and resolvable by location/station name as the existing filters allow).
2. Current temperature returns the most recent measurement's temperature with its timestamp (and source).
3. Last-day and last-week averages are computed over the trailing 24h and 7d windows via repository aggregation, not in-memory scans of all measurements.
4. Empty windows return an explicit "no data" response rather than an error or a misleading `0`.
5. The endpoints work uniformly over `manual` and `openweather` measurements (the pipeline already unified them).
6. Endpoints are documented with Swagger (`@ApiOperation`, params, responses) and return validated DTOs.
7. Inputs are validated (unknown station → 404, bad params → 400).
8. Unit tests cover the use cases (current, day avg, week avg, empty windows) and the new repository aggregation methods.

## Dev Notes

- Reuse the existing station resolution used by `QueryMeasurementsService` filters so "by station name/location" stays consistent with Delivery II.
- Compute windows from a single "now" passed into the use case so tests stay deterministic (per the testing rules — no reliance on system time inside domain/use-case logic).
- These endpoints are the primary targets of the k6 load tests (S-03.13); keep them efficient (aggregation + indexes), and they are good candidates for the short-TTL request cache.
