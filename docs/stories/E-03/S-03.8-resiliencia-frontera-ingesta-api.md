# Historia 3.8: Resiliencia en fronteras API ↔ ingesta

Estado: pendiente

## Historia

Como operador, quiero proteger la comunicación REST entre API e ingesta, para
que una API lenta no bloquee el scheduler de ingesta ni que una ingesta caída
degrade los reportes de temperatura actual expuestos al cliente.

## Criterios de aceptación

### Frontera ingesta → API (envío de mediciones, S-03.6)

1. El cliente interno tiene timeout y circuit breaker configurables.
2. Un bulkhead limita envíos simultáneos.
3. Solo se reintentan 429, 502, 503, 504 y errores de red seguros.
4. Los reintentos usan backoff con jitter y la clave de idempotencia de S-03.6.
5. Los errores definitivos se registran por estación sin cancelar el lote.

### Frontera API → ingesta (reporte temperatura actual, S-03.9)

6. El cliente HTTP de la API hacia ingesta tiene timeout configurable.
7. Un circuit breaker o bulkhead evita saturar ingesta ante picos de consultas.
8. Fallos de ingesta se mapean a respuestas HTTP claras sin exponer stack traces.
9. Los reintentos en el read path son conservadores (máximo 1) o están
   deshabilitados si aumentan latencia p95; la política queda documentada.

### Observabilidad y pruebas

10. Se exponen métricas de intentos, reintentos, rechazos y estado del breaker
    en ambas direcciones.
11. Las pruebas cubren saturación, timeout, retry seguro y fallo definitivo en
    cada frontera.
