# Story 3.9: Metrics Aggregation — Prometheus Instrumentation (Hardware/Endpoint/Business)

Status: draft

## Story

As an operator,
I want each service to expose Prometheus metrics covering hardware, endpoints, and business events,
so that system health and domain activity can be scraped, alerted on, and visualized.

## Acceptance Criteria

1. `api`, `notifications`, and `ingestion` each expose a `/metrics` endpoint in Prometheus format.
2. **Hardware/process metrics:** default Node/process collectors (CPU, memory/RSS/heap, event loop lag, GC) are enabled per service.
3. **Per-endpoint HTTP metrics:** request count and latency histogram labeled by method, route, and status code, via a global interceptor/middleware.
4. **Business metrics:** counters/gauges for `measurements_ingested_total{source}`, `alerts_published_total{alertType}`, `owm_requests_total{result}`, `ingestion_cycle_duration_seconds`, and `circuit_breaker_state` (from S-03.6).
5. A Prometheus service is added to `docker-compose.yml` and scrapes all three services on a configured interval.
6. Metric names/labels follow Prometheus conventions and avoid high-cardinality labels (route templates, not raw URLs).
7. Unit tests verify business counters increment on the right events; the `/metrics` endpoint returns a parseable payload.
8. The Prometheus datasource is provisioned in Grafana for the dashboard (S-03.12).

## Tasks / Subtasks

- [ ] Task 1: Metrics runtime (AC: #1, #2)
  - [ ] 1.1 Add a Prometheus client (e.g. `prom-client` / `@willsoto/nestjs-prometheus`) to each service.
  - [ ] 1.2 Enable default process/hardware collectors and expose `/metrics`.

- [ ] Task 2: HTTP metrics (AC: #3, #6)
  - [ ] 2.1 Add an interceptor/middleware recording a latency histogram + counter by route template/status.
  - [ ] 2.2 Guard against high-cardinality labels.

- [ ] Task 3: Business metrics (AC: #4, #7)
  - [ ] 3.1 Increment `measurements_ingested_total` / `alerts_published_total` in the pipeline path.
  - [ ] 3.2 Record `owm_requests_total`, `ingestion_cycle_duration_seconds`, and breaker state in ingestion.
  - [ ] 3.3 Unit-test counter increments on the corresponding events.

- [ ] Task 4: Prometheus + provisioning (AC: #5, #8)
  - [ ] 4.1 Add `prometheus` to `docker-compose.yml` with a scrape config for the three services.
  - [ ] 4.2 Provision the Prometheus datasource in Grafana.

## Dev Notes

- Keep a single metrics module/util shared via `libs/shared` so naming stays consistent across services.
- Business metrics are the differentiator for the dashboard's "business" section (ingested/min, alerts fired, OWM error rate) — wire them where the events actually occur in the pipeline and the ingestion cycle.
- Store the Prometheus config and Grafana provisioning under a versioned `infra/observability` folder.
